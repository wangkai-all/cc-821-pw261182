# 情景分析与应用说明

> 本文件中的公司、人、事件、日期和金额全部虚构，只用于演示再保条款的计算顺序、额度侵蚀与恢复机制。**不是保险、再保险、精算、税务或法律建议。**

## 1. 应用解决的核心问题

同样的全年损失总额，可能因为以下顺序产生不同分摊：

1. 哪一笔记入先，先侵蚀年度限额；
2. 大额事件是否把层额度一次打满；
3. 恢复额度是否已经生效，还是仍在等待笔数/生效限制内；
4. 迟到补损发生时，原事件免赔早已吸收，但当前年度余额可能已被其他事件占用；
5. 估损冲回必须减少原事件累计责任并回吐层赔款/恢复年度余额，而不是创建一个负的新事故。

应用把每次结算冻结为不可变版本。修改条款、新增补损/冲回或交换 A/B 顺序，都会生成新的 `v2、v3…`；旧版本的条款快照、两套流水顺序和完整结果仍可查看、导出 JSON。

## 2. 计算口径

### 2.1 金额和比例

- 金额：整数 **分**，例如 `¥100.01` 存为 `10001`。
- 比例：整数 **bps**，例如 `5% = 500bps`。
- 乘法中间值使用 `BigInt`，四舍五入规则为 `HALF_UP`。
- 共保份额尾差使用最大余数法，保证各份额之和恰好等于层赔款。

### 2.2 事件、流水和合同年度

- 一个事件包含 `initial`、`supplement`、`revision` 三类流水。
- `supplement` 为正增量，`revision` 输入正金额但引擎按负增量处理。
- 合同按事件的 `occurrenceDate` 匹配，而不是按补损入账日期。因此 2025 事件在 2026 年的补损仍回到 2025 合同和原事件。
- 结算顺序由 `orderA` / `orderB` 两个流水 ID 数组决定；校验要求所有流水恰好出现一次。

### 2.3 免赔和多层顺序

免赔按同一事件的累计损失计算：

```text
cumulativeLoss = initial + supplements - revisions
deductible     = min(cumulativeLoss, occurrenceDeductible)
```

冲回使累计损失下降时，免赔也可能回吐；之后再有补损，只继续吸收同一笔免赔的未用余额，不会重新产生一次免赔。

多层按明确的 `layer.order` 适用。每层先计算条款区间责任，再受事件累计、单次限额、年度有效额度限制。后序层还受不重复补偿残额约束，所以总结算始终满足：

```text
自留合计 + 各层摊回合计 = 原始损失合计
```

每笔流水也满足：

```text
该笔所有承担行金额之和 = 该笔有符号损失增量
```

### 2.4 年度额度和恢复

```text
有效年度额度 = annualLimit + 已生效恢复额度
可用余额     = 有效年度额度 - 年度已用净额
```

冲回导致层赔款为负时，会减少年度已用净额，从而恢复可用余额；已经使用的恢复次数和已产生的恢复费不自动撤销，这是本示范采用的条款口径。

当一笔正数支付把可用余额从 `>0` 打到 `0` 时，只生成一次恢复申请：

- 未超过 `maxCount`：生成 `PENDING` 恢复记录，计算费用；
- 超过次数：生成 `FAILED` 记录，原因码 `MAX_REINSTATEMENT_COUNT`；
- `waitEntries = k`：恢复在同一合同第 `grantContractSeq + k + 1` 笔流水开始前生效；
- 在生效前遇到的后续流水不能使用该额度，缺口原因码为 `REINSTATEMENT_PENDING_NOT_EFFECTIVE`。

## 3. 内置情景结论

| 情景 ID | 观察目标 | 关键可核对结果 |
|---|---|---|
| `order-effect` | 事件顺序改变 L1 摊回和自留 | 总损失均为 ¥740；A 自留 ¥180、层摊回 ¥560；B 自留 ¥280、层摊回 ¥460；B−A 自留 `+¥100` |
| `development` | 补损/冲回回到原事件，免赔不重复 | 最终损失 ¥300；免赔始终合计 ¥100；最终 L1 ¥200、L2 ¥0；补损笔免赔 Δ 为 0 |
| `cross-year` | 跨日历年补损与事故年度隔离 | E-25 累计 ¥440 用 C-2025 限额；E-26 ¥180 用全新 C-2026 限额；总层摊回 ¥380 |
| `exhaustion-failure` | 年度限额耗尽、恢复次数有限且最终失败 | X1–X3 各摊回 ¥200，X4 摊回 ¥0、缺口 ¥200；两次恢复费各 ¥10 |
| `reinstatement-wait` | 恢复有生效笔数限制 | W1 后申请恢复，紧邻 W2 不可用并形成 ¥200 缺口，W3 才可用；交换 W2/W3 会交换具体事件结果 |
| `rounding-tail` | 定点数和一分尾差追踪 | ¥100.01 分为 ¥33.33、¥33.33、¥33.35；尾差归 P3，规则和权重写入 JSON |

## 4. 推荐网页操作路径

1. 顶部选择 **“顺序改变分摊”** 样例。
2. 在 **① 顺序比较** 查看 A/B 两套事件顺序、总量差异、按层和按事件差异。
3. 点击 **“交换 A/B 两套事件顺序并重算新版本”**，到 **⑤ 结算版本** 可看到原 `v1` 仍保留，新结果为 `v2`。
4. 进入 **② 条款 / 补损编辑**：
   - 选择合同和层，修改起赔点、单次限额、年度限额、恢复次数/费用/等待笔数；
   - 或选择原事件，加入一笔 `supplement` / `revision`。
5. 进入 **③ 事件前后额度**，选择事件和 A/B 顺序，查看每层事前可用、事件摊回、缺口、事后可用和待生效恢复。
6. 进入 **④ 逐笔流水核对**，逐层查看目标责任 Δ、结算前可用、实际支付 Δ、缺口 Δ、结算后余额、恢复记录和尾差记录。
7. 在 **⑤ 结算版本与说明** 导出任一版本 JSON。JSON 包含输入快照、完整流水、汇总、恢复和尾差记录，可用于外部复核。

## 5. 如何扩展

核心引擎不依赖 DOM：

```js
import { settleStream, compareRuns } from './src/core/engine.js';

const runA = settleStream(workbook, workbook.orderA, { orderKey: 'A' });
const runB = settleStream(workbook, workbook.orderB, { orderKey: 'B' });
console.log(compareRuns(runA, runB));
```

新增样例时，在 `src/core/scenarios.js` 中加入 workbook，并确保：

- 合同 ID、事件 ID、流水 ID、层 ID 唯一；
- 每个 `orderA/orderB` 包含全部流水 ID 恰好一次；
- 所有金额使用 `Y('123.45')` 或整数分；
- 若加入新的分配规则，同时在 `test/engine.test.js` 增加手算断言。
