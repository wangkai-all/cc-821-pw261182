# 可手算流水逐层核对

> 所有主体、事件和条款均为虚构。金额下表以 **元** 展示；程序内部使用整数 **分**，比例使用整数 bps（`500bps = 5%`）。因此 `¥100.01` 在引擎中是整数 `10001`，不存在浮点误差。

核对路径：

```bash
npm test
npm start
# 打开 http://localhost:4173/ → “④ 逐笔流水核对”
```

测试文件 `test/engine.test.js` 固化了本文的关键数字。

## 1. 事件顺序：同一全年损失 ¥740，分摊相差 ¥100

条款 `C-ORD-2025`：

- 每次事故免赔：`40`
- 第一层 `L1`：`160 xs 40`，单次限额 `160`，年度限额 `160`
  - 可恢复：`1` 次，每次 `160`
  - 恢复费用：`160 × 5% = 8`
  - `waitEntries = 0`：恢复额度自**下一笔同合同流水**起可用，不追溯补到触发笔
- 第二层 `L2`：`300 xs 200`，单次/年度限额 `300 / 600`，无恢复

事件：

- `E-BIG`：损失 `600`
- `E-MID`：损失 `140`

### 顺序 A：`BIG → MID`

| 笔 | 事件 | 累计损失 | 免赔 Δ | L1 事前可用 | L1 摊回 Δ | L1 事后可用 | L2 摊回 Δ | 未分配 Δ | 本笔平衡 |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | BIG | 600 | 40 | 160 | 160 | 0；随后生成待下一笔生效的恢复 160 | 300 | 100 | 40+160+300+100=600 |
| 2 | MID | 140 | 40 | 160（恢复已激活） | 100 | 60 | 0 | 0 | 40+100=140 |

第一笔明细：

- BIG 超过 `200 + 300 = 500` 的部分为 `100`，高层没有更多层，进入未分配自留。
- L1 把年度 `160` 打满，产生第 1 次恢复，费用 `8`。

顺序 A 合计：

| 项目 | 金额 |
|---|---:|
| 原始损失 | 740 |
| 免赔 | 80 |
| L1 摊回 | 260 |
| L2 摊回 | 300 |
| 未分配/超层自留 | 100 |
| **自留合计** | **180** |
| **层摊回合计** | **560** |
| 恢复费用 | 8 |

### 顺序 B：`MID → BIG`

| 笔 | 事件 | 累计损失 | 免赔 Δ | L1 事前可用 | L1 摊回 Δ | L1 缺口 Δ | L1 事后可用 | L2 摊回 Δ | 未分配 Δ |
|---:|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | MID | 140 | 40 | 160 | 100 | 0 | 60 | 0 | 0 |
| 2 | BIG | 600 | 40 | 60 | 60 | **100** | 0；生成恢复 160，但本笔不可追溯使用 | 300 | 100 |

第二笔平衡：

```text
免赔 40 + L1 摊回 60 + L1 年度限额缺口 100
+ L2 摊回 300 + 未分配超层 100
= 600
```

顺序 B 合计：

| 项目 | 金额 |
|---|---:|
| 原始损失 | 740 |
| 免赔 | 80 |
| L1 摊回 | 160（MID 100 + BIG 60） |
| L2 摊回 | 300 |
| L1 限额缺口 | 100 |
| 未分配/超层自留 | 100 |
| **自留合计** | **280** |
| **层摊回合计** | **460** |
| 恢复费用 | 8 |

**结论：B−A 的自留差异为 `+100`，层摊回差异为 `−100`。**  
B 顺序中恢复批单仍生成并收取费用 `8`，但年末没有下一笔流水来使用它。示范条款明确把“自动出具恢复批单”作为收费时点；若不希望对未使用恢复收费，可把费用率改为 `0` 或把规则改成需单独申请。

## 2. 补损与冲回回到原事件：免赔 ¥100 只用一次

合同：

- 每次事故免赔 `100`
- `D-L1`：`200 xs 100`，年度限额 `500`
- `D-L2`：`300 xs 300`，年度限额 `300`

同一事件流水：

1. 首次估损：`+250`
2. 迟到补损：`+120`
3. 估损冲回：`−70`
4. 最终累计损失：`250 + 120 − 70 = 300`

### 时间顺序 A：`+250 → +120 → −70`

| 笔 | 累计损失前→后 | 免赔 Δ | D-L1 Δ | D-L2 Δ | 说明 |
|---:|---|---:|---:|---:|---|
| 1 | 0 → 250 | +100 | +150 | 0 | L1 覆盖 `100..250` 的 150 |
| 2 | 250 → 370 | **0** | +50 | +70 | L1 补足 200 限额；`300..370` 进入 L2 |
| 3 | 370 → 300 | 0 | 0 | **−70** | 从最上层冲回，L2 累计归零 |

最终：

```text
免赔 100 + D-L1 200 + D-L2 0 = 300
```

第 2 笔若被错误当成新事故，会再扣一次 `100` 免赔；程序中该笔免赔 Δ 为 `0`，测试已固化。

### What-if 顺序 B：`+250 → −70 → +120`

| 笔 | 累计损失前→后 | 免赔 Δ | D-L1 Δ |
|---:|---|---:|---:|
| 1 | 0 → 250 | +100 | +150 |
| 2 | 250 → 180 | 0 | −70（L1 累计 80） |
| 3 | 180 → 300 | 0 | +120（L1 累计 200） |

最终仍是免赔 `100`、L1 `200`、总损失 `300`，但中间逐层流水不同。

## 3. 跨年度：2025 事件在 2026 年补损

- `E-25` 发生日：`2025-12-20`，明确归属 `C-2025`
  - 2025-12-22 首次估损：`180`
  - 2026-01-08 补损：`260`，累计 `440`
- `E-26` 发生日：`2026-01-05`，归属 `C-2026`
  - 首次估损：`180`

两个合同均为免赔 `100`、第一层 `300 xs 100`、年度限额 `300`。

按入账交错顺序：`M-25-1 → M-26-1 → M-25-2`。

| 笔 | 合同/年度 | 计算 | 结果 |
|---:|---|---|---:|
| 1 | C-2025 | 180：免赔 100 + 层 80 | 2025 层余额 220 |
| 2 | C-2026 | 180：免赔 100 + 层 80 | 2026 新额度余额 220 |
| 3 | C-2025 | 补 260：免赔 Δ 0；L1 增加 220 至限额 300；超 `400` 以上 40 未分配 | 2025 层用尽 |

最终：

- `E-25`：免赔 `100` + 2025 层 `300` + 未分配 `40` = `440`
- `E-26`：免赔 `100` + 2026 层 `80` = `180`
- 全年两个事故年度合计：损失 `620`，层摊回 `380`，自留 `240`

把 E-25 的两笔流水连续重放、再处理 E-26，结果相同，因为年度额度按合同隔离。

## 4. 限额耗尽与恢复次数失败

合同 `C-EXH`：

- 免赔 `100`
- `X-L1`：`200 xs 100`，单次/年度初始额度均为 `200`
- 最多恢复 `2` 次，每次 `200`，费用 `5% = 10/次`，等待 `0` 笔
- 四笔事件损失均为 `300`，所以每笔条款层责任均为 `300 − 100 = 200`

| 事件 | 事前有效额度 | 本笔摊回 | 事后额度 | 恢复记录 |
|---|---:|---:|---:|---|
| X1 | 200 | 200 | 0 | 第 1 次恢复 200，费用 10，下一笔可用 |
| X2 | 200 | 200 | 0 | 第 2 次恢复 200，费用 10，下一笔可用 |
| X3 | 200 | 200 | 0 | 第 3 次申请超过上限 2，**失败** |
| X4 | 0 | 0 | 0 | `200` 转为年度限额/恢复失败自留缺口 |

合计：

```text
总损失 = 4 × 300 = 1200
免赔   = 4 × 100 = 400
层摊回 = 3 × 200 = 600
缺口   = 200
自留   = 400 + 200 = 600
恢复费用 = 10 + 10 = 20
```

## 5. 恢复生效限制：等待 1 笔流水

合同 `C-WAIT`：

- 免赔 `100`
- `W-L1`：`200 xs 100`，年度额度 `200`
- 可恢复 `1` 次，每次 `200`，费用 `10`
- `waitEntries = 1`：恢复申请后，需经过 **1 笔同合同后续流水**，再下一笔开始前才生效

顺序 A：`W1 → W2 → W3`。

| 合同流水序号 | 事件 | 事前额度 | 摊回 | 缺口 | 恢复状态 |
|---:|---|---:|---:|---:|---|
| 1 | W1 | 200 | 200 | 0 | 申请恢复；`availableAtContractSeq = 1 + 1 + 1 = 3` |
| 2 | W2 | 0 | 0 | 200 | 仍需等待，原因码 `REINSTATEMENT_PENDING_NOT_EFFECTIVE` |
| 3 | W3 | 200 | 200 | 0 | 开始前激活恢复；本笔用尽后第 2 次恢复申请失败 |

因此 A 中 W2 自留 `300`（免赔 100 + 缺口 200），W3 层摊回 `200`。

顺序 B：`W1 → W3 → W2` 时，落空的是中间位置的 W3，最后 W2 使用已生效额度。总摊回仍是 `400`，但**具体事件承担发生交换**；事件比较表可直接核对。

## 6. 定点尾差：最大余数法

层赔款总额 `10001` 分，即 `¥100.01`。三个共保人权重：

- P1：`3333bps = 33.33%`
- P2：`3333bps = 33.33%`
- P3：`3334bps = 33.34%`

| 份额 | 精确商（分） | floor 后 | 小数余数比较 | 尾差 | 最终（分） | 最终（元） |
|---|---:|---:|---|---:|---:|---:|
| P1 | 3333.3333 | 3333 | 0.3333 | 0 | 3333 | 33.33 |
| P2 | 3333.3333 | 3333 | 0.3333 | 0 | 3333 | 33.33 |
| P3 | 3334.3334 | 3334 | 0.3334，最大 | +1 | 3335 | 33.35 |

```text
33.33 + 33.33 + 33.35 = 100.01
```

规则标识：`LARGEST_REMAINDER__TIE_CLAUSE_ORDER`。若余数相同，则按份额的 `tailPriority`，再按数组顺序分配。每一笔尾差都会写入 `run.tailRecords` 和网页流水卡片。

## 7. 多层不重复计算规则

对累计事件损失 `L`、免赔 `D`，程序先得到：

```text
deductible = min(L, D)
residual   = L - deductible
```

然后按 `layer.order` 逐层：

```text
raw_i    = min(occurrenceLimit_i, max(0, L - attachment_i))
target_i = min(raw_i, residual)
residual = residual - target_i
```

再叠加年度限额和恢复额度形成实际支付。这样即使两层起赔点重叠或条款解释竞争，后序层也只能对“扣除免赔和先序层后的未分配损失”承担，不可能出现各层独立算完后赔款之和超过原始损失。
